# Tokenizer: local search checkpoint

`src/tokenizer/` composes Field, BaseTypeahead, and removable Tokens. The caller owns selected items and receives the next list with typed add/remove metadata. Already-selected IDs are excluded from search. Named fields submit repeated token IDs in selection order; disabled fields do not submit values. Removing a token moves focus back to the search input.

## Inline Clear all checkpoint

Opt in with `TokenizerWithClear`, which accepts the existing `TokenizerProps`. The current `Tokenizer` remains unchanged for callers that don't opt in. The action appears only on enabled fields with a removable selection. It uses the same removal policy as the individual token buttons, retains locked tokens in selection order, and sends one controlled change with `Remove(last_removable_item)`. It returns focus to the same search input and queues the localized “All items removed” message through the shared polite channel. The Tags showcase exercises the action and displays the callback count and metadata.

The pinned API spells this `hasClear` on `Tokenizer`. Adding `has_clear` to the exported Rust props would break exhaustive struct construction and destructuring, so exact API spelling is blocked under the no-break constraint. The locked-item policy is internal; no production composer (including PowerSearch) supplies it yet. PowerSearch's copy override, empty-search Backspace, upstream touch focus handling, end-lane layout parity, and confirmed sheet Clear all are not part of this checkpoint. Browser coverage for key and pointer activation, focus/identity, form values, and the polite region was added to `tests/tokenizer.browser.mjs` but not run. Spoken and visual parity remain unverified.
