# SideNavHeading checkpoint

`src/side_nav/side_nav_heading.rs` ports the expanded, non-menu forms: static heading, whole-heading link, and independent links for the title and surrounding text. Trailing controls sit beside the whole-heading link rather than inside it. Whole-heading and icon links use the shared link renderer and destination validation.

Source: Meta Astryx `476a3153417dbf75c565f7df05b0784e94ddd59e`, `SideNav/SideNavHeading.tsx` (`f19b5d0bcd2e2bba44e99a508bf07d6709d5fa3b`), the component spec (`4f70cd1d000a00f3424721e94d810235ec66f9ee`), and both catalog templates. The showcase adapts the templates with a local icon; Basic now uses the actual expanded `SideNav` header slot. The migration checklist stays open.

At the initial checkpoint, all five standard Rust checks passed, as did the Link and showcase navigation regressions. Chrome verified the then-current linked rows and separate trailing focus (DOM/focus), a link name (AX), and minimum height (geometry). Those results do not establish paint, raster parity, or spoken output.

The focused SSR follow-up verifies the expanded header composition, the source's identity title (not a document-outline heading), independent native destinations, the named icon link, renderer precedence and blocked destinations, and a sibling trailing action. Empty destinations no longer create a link or split a whole-row link; nonempty values still go to the shared destination policy. The leading artwork slot is for noninteractive content.

`tests/side_nav_heading.browser.mjs` now scopes its AX assertions to the individual link and button DOM nodes and checks Tab/Enter isolation between the native fragment link and trailing action. The updated test was syntax-checked only. An integrator must run it against a new showcase build. Source-comparative geometry and paint (including RTL and focus), published raster parity, and manual screen-reader speech remain unverified.

The menu gate needs a shared non-dialog menu surface, a single named `NavHeadingMenu`, and the shared hover hand-off/delay, press tracking, and dismissal/focus-return contracts. The current `Popover` component renders a dialog and the inline `NavHeadingMenu` delegates show/dismiss to its host; wrapping it in another menu or adding heading-local copies of those mechanisms would not close the gate. A public `menu` prop also needs API approval in this worktree. The collapsed forms and automatic hiding of trailing content depend on SideNav publishing its collapse context; the current expanded rail does not. The pinned source assigns no document heading level; adding one would need an approved semantics/API decision.
